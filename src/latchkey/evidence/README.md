# Evidence delivery transports

`adapters.mjs` is a client-side transport module. Never expose it as a server URL-fetch proxy: self-hosted Evidence deliberately accepts buyer HTTPS origins, including private networks, and literal HTTP loopback installations. Other destinations allow only their exact official HTTPS origins. Endpoint paths are fixed by the adapter; credentials, URL userinfo, query strings and redirects cannot select another host.

The caller verifies the signed `packageValue`, previews its fields, confirms authorization immediately before dispatch, and retains the package and delivery obligation. The module does not persist credentials, sign packages, approve compliance, automatically retry, or log request and response content. Bearer credentials are strings; Secureframe uses `{apiKey,keySecret}`. `target` is an existing Evidence requirement ID, Vanta document ID, Secureframe test ID, or Drata evidence name. Drata additionally requires a positive numeric workspace ID. Dates are UTC `YYYY-MM-DD`.

The result is `{state,providerReference,retryable,status,stage}`. `stage` is a checkpoint object with `name`, package and destination `binding`, and, after a successful Vanta and Drata upload, `uploadReference`. A caller can pass a previous failed `submit` or `create` stage as optional `resume` to skip the completed upload. Preserve it privately. A completed checkpoint cannot be resumed. Each call attempts each remaining stage once. Treat transport failures and malformed success responses as ambiguous backlog with `retryable:false`; reconcile provider state before another create. Retryability on an HTTP error describes the failed stage only. Never restart the whole flow blindly after a partial success.

Vanta upload is draft until submit succeeds. Drata creation requires both artifact counters and the returned artifact list to confirm the single requested artifact. Secureframe's published operation has a default response without a successful ID schema: HTTP success is transport acceptance and `providerReference` remains null unless a same-origin Location header is returned. Show that missing reference honestly. No adapter claims auditor approval, external erasure, or signature verification by the receiver.

## Approved company disclosures

Company evidence is available from the vault console. Capture is explicit and scoped to one company vault owned by the caller; private-work and family vaults are refused. The snapshot reports observed current direct-member enrollment and allowlisted vault-related security-event counts. It does not infer usage, workforce-wide adoption or MFA from an enrolled device. MFA is exported as unknown with null enforcement and measurement-source timestamps until LKY-008/051 supply actual authoritative factor/policy observations. LKY-013 inherits actual usage and adoption-denominator obligations.

Outbound access reviews omit person and recipient identities, credential references, arbitrary reasons and the free-form review period. The local attributed immutable review remains available through its own authorized review door. Each destination gets an independent current field preview and explicit consent. The owner signs the exact disclosure under the approved-evidence signing context; dispatch validates the current source, exact fields, signature and destination revision. The exact signed bytes remain with the local delivery obligation through rejection or outage. Credentials remain only in client memory. Acceptance and provider references are client-reported transport results, never auditor approval.

Each destination has an owner-selected maximum source age (24 hours initially). Preview displays source time and stale-after time. Stale sources cannot dispatch; capture a new posture snapshot, complete a fresh review, or explicitly configure the destination age policy and preview again. Nothing dispatches automatically. Revocation or person erasure invalidates pending disclosures before the next dispatch. Erasure removes affected snapshots, signed delivery packages and attributed review packages; remaining anonymous external-deletion records lose their old source reference. Restored captures and destinations are inactive. LKY-027 inherits the personal and family domain exclusion as its full account clients land.

External deletion is a separate record of work the owner performs in the provider's interface. Record the actual request reference, retain pending-provider-confirmation, then separately consent to recording the observed provider confirmation reference. These states are explicitly owner-reported; Latchkey neither sends an automatic deletion request nor claims independent provider verification. Destination revoke, upload acceptance, local erasure and provider confirmation are distinct. Missing provider references remain unknown and require provider inspection before recording follow-up. No automatic retry, destructive external operation or certification claim is introduced.

## Interrupted provider writes

`EvidenceClient.send` allocates a stable delivery ID before the authorization call. Repeating that authorization with the same ID and exact signed package returns the existing operation. Every provider write first claims a durable attempt on that delivery. The attempt records its stage, ID, start time and one-minute lease; expiry reports an outstanding attempt and never grants permission to repeat an ambiguous write. Current source, owner, destination revision and freshness are checked before each next write.

After a validated Vanta or Drata upload response, the upload reference is saved before submitting or creating evidence. A new client can inspect `delivery(id)` and explicitly consent to `resumeUpload(id, credential, true)` only from an acknowledged upload checkpoint. This skips the upload. Concurrent resumes cannot both claim the next attempt. An in-flight or ambiguous operation requires provider reconciliation; it cannot use this resume door. A lost final local acknowledgment can replay the exact `evidence` result call without changing the recorded outcome or adding another audit event. Different outcomes conflict. Attempt history and signed packages remain in the existing Records domain; restored destinations remain inactive and person erasure removes affected delivery checkpoints.

`inspectUpload(id, credential)` performs bounded read-only Vanta inspection using the saved upload reference and the official uploaded-files schema. It follows at most ten pages of one hundred entries, refuses repeated cursors and redirects, and checks current authorization before every page. Missing, deleted, mismatched, malformed and rate-limited observations stay unknown or explicitly not found. It returns only the matching reference and observation metadata. Seeing a file does not establish that document submission succeeded, does not close an ambiguous write and never triggers another provider mutation. Unknown outcomes on the other transports still require inspection in the provider interface. This is bounded evidence-family behavior, not completed LKY-052 coverage of every integration family.

[Vanta uploaded-files schema](https://developer.vanta.com/api-reference/documents/list-documents-uploads.md), consulted 24 October 2026, specifies the reference, file metadata and cursor pagination used by this inspection.

Inspection reserves a durable one-minute lease before any provider read. A competing or restarted client is refused until the recorded next-allowed time. The bounded ten-page read has one fifteen-second transport deadline. Diagnostics on the delivery retain only client-reported presence, status, page count and timestamps. Successful inspection waits at least thirty seconds; unknown outcomes back off exponentially, capped at one hour, and honor a provider Retry-After up to one day. Interrupted inspections remain blocked until the lease expires. None of these observations authorize another write or establish successful submission.
