# Buyer-held Records custody

`scripts/latchkey/records-commands.mjs` exports `recordsCommand(command,input,{client}?)` and the named functions below. It is a dispatcher for the owning CLI, with no ambient credential discovery, stdin reading or stdout output. All paths select explicit files. Archive inputs must be owner-owned regular files with no group/other permissions; outputs must be new paths with existing parent directories.

- `sealRecordsArchive({input,output,exportKey})`: validates a complete Base v2 archive, encrypts its exact bytes, verifies the encrypted result and publishes an owner-only output. `exportKey` is a 32-byte `Uint8Array` or canonical base64url string. The format is bounded JSONL: a versioned header, 64 KiB AES-GCM chunks and an authenticated final commitment to the chunk count, byte count, raw SHA-256 and Base archive digest. HKDF derives an archive-specific key; header, index and record kind are authenticated. It preserves all domains supported by the supplied Base policy.
- `openRecordsArchive({input,output,exportKey,laterJournal?})`: authenticates every chunk and final commitment, runs Base's complete manifest/part/content/archive verifier, then publishes the exact Base bytes. Corrupt, reordered, truncated or trailing records never promote output. Unverified bytes live only in an owner-only scratch file that is deleted on failure. A supplied later journal is a **decrypted Base archive** verified in full and checked for matching source and a later/equal epoch. This function does not apply erasure fences; pass that same journal to Base import.
- `inspectRecordsArchive(input)`: returns `{manifest,closing}` only after Base verifies the complete private file. Use that verified receipt to bind downstream decisions.

The archive envelope does not manufacture a Records policy, strip rows or authorize restore. The owning integration must use the edition's policy to exclude live authority, gate export, stop writers, validate destination eligibility and call Base's atomic import machinery. The receipt explicitly warns that an offline archive cannot prove subsequent erasure; supplying a later journal still cannot prove it is the latest one. The encrypted format never adds bearer sessions or live grants.

## Destination recipient preparation

Identity objects contain `{account,tenant,recipientKey,authorityKey}`. Fingerprints match the existing client protocol: `digest(JSON.stringify([recipientKey,authorityKey]))`. Both source and destination fingerprints must come from an independent verification ceremony, not an untrusted archive or directory response.

1. `planDestinationRewrap({input,source,destination,sourceFingerprint,destinationFingerprint})` validates the raw Base archive and its source account's pinned keys. It returns `{plan,planHash}` with exact archive digest/source identity, source-owned vault revisions and the verified destination. `unapprovedVaults` enumerates other owners' vaults. An integration must obtain their approvals too; an empty owned set does not authorize them.
2. Show the exact plan to the source owner. `approveDestinationRewrap({input,plan,approvedPlanHash,client,purpose,expiresAt,now?})` requires the explicitly accepted hash and that owner's unlocked `VaultClient`. It revalidates the archive and plan, unwraps each archived owner key using the pinned source authority, creates signed wraps for the destination recipient and signs the complete decision. It returns `{decision,signature}` without writing product state.
3. `verifyDestinationRewrap({plan,approval,sourceFingerprint,destinationFingerprint,now?})` verifies the approval, expiry, exact destination/plan, source signature and every wrapped-key signature. It returns `{valid:true,activeAuthority:false,unapprovedVaults}`. The destination must compare the plan against its verified archive and current destination identity; verification alone never activates access.

Each output wrap has `rights:[]`. Historical grants remain historical. Existing item keys and AEAD contexts bind the **source tenant**; these wraps preserve that context and do not silently relabel ciphertext to the destination tenant. The approval separately binds the destination tenant. Tenant/account mapping, importing the wraps, source-owner attribution after transfer and a separately reviewed activation ceremony belong to the integrated restore. Account-root/device/recovery private keys are never copied.

## Applying an actual restored installation

`service.mjs` exports `portabilityAuthenticated(route,input,context)` (also named `portabilityResponse`) and `RecordsError`. Mount it after the normal authenticated device/grant/signature/nonce checks and before ordinary vault lookup. Its context is `{db,env,now,actor,device,tenant,session,fence,fenceArgs}`. It returns a plain result or null for unrelated paths; errors expose only `{code,status}`. Apply migration `0021_latchkey_restore.sql`. Exclude `lky_restore_preparations` and `lky_restore_guard` from Records: they contain destination-local capabilities. Preserve `lky_restore_history`, which holds historical attribution without a usable approval or wrapped key.

The service requires a currently active installation owner with an unlocked, independently enrolled/recovered destination device. The destination account must differ from the approving source vault owner, and its tenant must equal the restored source tenant. A foreign tenant is refused; ciphertext is never silently relabelled. An imported operator role alone provides no item access.

- `archive/prepare` accepts `{plan,approval,sourceFingerprint,destinationFingerprint}`. Plans and source-signed decisions include both Base `archiveHash` and `contentHash`. The service finds a completed Base import, replays its retained verified parts with Base's own verifiers and compares the exact archived source keys and owned vault inventory. It requires the current imported vault ownership/epoch/revision and every historical recipient to remain inactive. It stores only an inactive preparation, with idempotence for the same plan and signed approval.
- `archive/status` accepts `{restore}` and returns the destination owner's preparation. Prepared status includes the signed plan/approval for local unwrapping; activated status is a receipt. Other identities cannot inspect it.
- `archive/activate` accepts `{restore,approvedPlanHash,activation,rights,wraps}`. `activation` names the destination person's explicit decision and `rights` must explicitly select the six owner rights. The destination client locally unwraps the source-approved keys and supplies freshly self-signed destination wraps. The service checks source approval expiry, exact plan/vault versions, both current identity keys, original completed import and live destination authority. One guarded transaction changes ownership, increments vault revisions, adds only the destination recipient rights, records durable historical attribution and completes the preparation. Original recipients retain `[]`; their grants do not activate. Same-name retries recover the completed receipt without repeating effects.

`new PortabilityClient(unlockedVaultClient)` provides `prepare`, `status(restore)` and `activate({restore,approvedPlanHash,activation,rights})`. Raw vault/account/device private keys never cross this API. The client pins its intentional new ownership after successful activation. Source-approved wraps do not replace independent destination sign-in or account recovery, and they do not enable schedules, links, machines or provider credentials.

`tests/latchkey-restore.mjs` exports `exerciseRecordsRestore` for the emitted-Worker journey after actual Base import and independent destination owner enrollment. It checks public route refusals, inactive preparation, explicit activation, decoded values and idempotent audit. This helper does not manufacture a restore receipt or simulate an application route.

Run the two real Base/D1 command tests with `node --test tests/latchkey-records.test.mjs` through the home's heavy-slot wrapper. The dedicated vault-browser Verify shard runs these command journeys and the bounded local restore tests.
